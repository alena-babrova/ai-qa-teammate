**GitHub Actions (headless).** The workflow **target** **`__ISSUE_KEY__`** is **often a Sub-task** (e.g. Test design)—**only a trigger** to run the pipeline. **`__STORY_KEY__`** is the **canonical User Story** (or parent Epic if your workflow resolves to that): same as the target when the target **is** the story, **or** the **parent** when the target is a **Sub-task** (CI pre-resolves via `resolve-output-key.js`). **All** material used to **design** tests—**Description**, acceptance-style fields, scope—must come **only** from **`jira_getIssue(__STORY_KEY__)`**, never from the Sub-task’s **description** or **summary** when **`__ISSUE_KEY__` ≠ `__STORY_KEY__`**. Use **`__STORY_KEY__`** for **`generated/jira-tests/...` paths**, story **browse links**, **`tests[].summary`** prefixes, and **linking** new Test issues to the **story**.

1. Follow **`.cursor/rules/ai-test-generator.mdc`** (canonical schema, no interactive questions) and **`.cursor/rules/jira-test-create.mdc`** (project, **Test** type, Test Steps / Expected custom fields).
2. Follow **`.cursor/skills/jira-story-test-cases-md/SKILL.md`**, especially **`## Headless CI (this repository, GitHub Actions)`**, for how to derive tests from the story.
3. **Task (order matters):**
   - **Step 0 — Verify keys:** Read **`__ISSUE_KEY__`** and **`__STORY_KEY__`**. If they **differ**, **`__ISSUE_KEY__`** is **not** the requirements source—treat it as pipeline trigger only. Proceed using **`__STORY_KEY__`** for every Jira read that drives test design and for every output path / summary / Test link. Optionally confirm with **`jira_getIssue(__STORY_KEY__)`** that the issue type is appropriate (e.g. Story); do **not** switch to using **`__ISSUE_KEY__`** for requirements.
   - **Step A — Story only for requirements:** Call Jira MCP (e.g. **`jira_getIssue`**) for **`__STORY_KEY__`** (the **first** substantive Jira fetch for scope). Request at least **`summary`**, **`description`**, **`issuetype`**, **`parent`**, and—if your tool allows—custom fields for **Acceptance Criteria** / **DoD** on **that** issue. **Test generation uses only this response** for scope: story **Description**, story **summary** (title context only), and story AC-style fields. **Do not** use the Sub-task’s **`description`**, **`summary`**, or other fields as a source of test scenarios when **`__ISSUE_KEY__` ≠ `__STORY_KEY__`**.
   - **Step B — Sub-task:** When the keys differ, **do not** **`jira_getIssue(__ISSUE_KEY__)`** to gather requirements. **Never** backfill from the Sub-task body.
   - **Step B2 — Empty story:** If **`__STORY_KEY__`** has **no testable content** (see **`.cursor/rules/ai-test-generator.mdc`** → **Empty story — do not create tests**): write **`tests.json`** with **`"tests": []`**, **`meta.json`** with **`"jiraPublish": "mcp"`** and **`"mcpCreatedKeys": []`**, **skip** Jira Test creation, **stop** (CI verification allows this).
   - **Step C — Write files:** **`generated/jira-tests/__STORY_KEY__/tests.json`** and **`meta.json`** only—**never** put those files under **`__ISSUE_KEY__`** when the keys differ. Each **`summary`** must **include `__STORY_KEY__`** when there are tests (see **`.cursor/rules/jira-test-cases-epmrpp-style.mdc`**).
   - **Step D — Jira Tests:** When **`tests`** is **not** empty: create **every** Test issue via MCP and **link each Test to the story (`__STORY_KEY__`)**. Then **`meta.json`** (`jiraPublish`, `mcpCreatedKeys`) per the rules.
4. Do **not** ask questions; do **not** put secrets in files.
